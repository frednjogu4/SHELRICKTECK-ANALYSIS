FREDRICK AURUM LOCAL UPDATE — 24 NOVEMBER 2026 (delivery repair)

What changed
- Every approved dashboard, chart, CSS, navigation and layout update now reaches BOTH http://127.0.0.1:8788/app and Cloudflare staging from ONE canonical build. Root cause of the old mismatch: the bridge sent /app with no cache headers and no validator, so the browser (and the service worker's copy of it) kept showing the previous layout even after the files on disk were current; nothing detected or announced a new release either.
- Release identity: every build stamps a content-addressed Build ID (scripts/build-revision.mjs) into dist/index.html (meta aurum-build), dist/build.json, dist/sw.js (release-keyed cache name) and, through the normal postbuild sync, into bridge/app.html + bridge/pwa/build.json. The id changes only when the built UI really changes; rebuilding the same sources always yields the same id (verified twice in a row).
- Local bridge: /app is now served with Cache-Control: no-cache + ETag + Last-Modified and answers If-None-Match with 304, so a replaced app.html appears on the very next reload. A new GET /build.json reports the release of the page it serves (id, version, git sha when the package sits in a checkout, app.html mtime as Last UI update, mode LOCAL or LOCAL DEV (watch)) with Cache-Control: no-store.
- New development mode: npm run dev:local runs vite build --watch plus the postbuild sync, so a source edit in index.html/, src/, styles or public/ rebuilds and syncs bridge/app.html automatically; the open tab detects the new Build ID within its poll and shows a non-intrusive NEW VERSION AVAILABLE banner (Refresh button, or one automatic refresh only when no form submission, modal, focused field or unsubmitted input is present). A .dev-watch.json marker (removed on exit) makes /build.json report LOCAL DEV (watch) so development and packaged mode are distinguishable. Supporting commands: npm run sync:local (copy now) and npm run verify:local (fail when any served copy differs from dist/).
- Service worker v3 lifecycle: the cache VERSION is stamped with the release id on every build; online navigations fetch with cache: no-store (the stale-shell fix); background refreshes revalidate with no-cache; activate() deletes only caches of older releases; /api, /bridge and /build.json are never cached; live API/WebSocket/auth traffic is still never stored. No browser storage is cleared wholesale.
- Settings has a new Build & delivery panel: Application version, Git commit, Build ID, Build timestamp, Environment (LOCAL / LOCAL DEV (watch) / STAGING), UI source revision, Service worker version, API health (GET /api/health), Bridge health and Last UI update. No secrets, tokens or account data are shown.
- Cloudflare staging serves the same release: /build.json runs through the Worker (enriched with the deployed commit when the platform provides it) and reports the same Build ID as the page; staging and local package UI derive from one canonical build (dist/ -> bridge/ copies are checked byte-for-byte by tests).
- Startup (bridge/SETUP_AND_RUN.bat) now verifies app.html exists, warns when pwa/build.json is missing, and prints the local UI release id before opening the browser. It still checks required files, starts services once (ports 8787/8788 are freed first), never logs bridge tokens and opens http://127.0.0.1:8788/app only after the local server is ready.
- New npm scripts: dev:local, sync:local, verify:local (added alongside the existing build/verify:dist; no existing command was replaced). Regression tests cover build-revision consistency, stale-copy detection, service-worker cache lifecycle, update-banner gating and the bridge cache/304/build.json behaviour (node + Python suites).
- One-click Windows updater (UPDATE_LOCAL_APP.bat): double-click UPDATE_LOCAL_APP.bat (even from Downloads) to locate the active local package folder serving http://127.0.0.1:8788/app, download and verify the latest GitHub main release, restart both the local API (4100) and bridge (8788) without touching Exness MT5 or local tokens/data, verify http://127.0.0.1:8788/build.json matches the new Build ID, and create a Desktop "Fredrick TRADING - Update Local App" shortcut for one-click future updates.

Limit
- The running bridge process itself needs no restart after a build (it reads app.html per request), but a bridge started from an OLD package folder keeps serving old files until the package is updated: either double-click UPDATE_LOCAL_APP.bat (one-click automatic sync + restart + live Build ID check) or extract this ZIP over the package folder and run START_ALL_LOCAL.bat again; the startup line "Local UI release: b..." and Settings -> Build & delivery must match the Build ID shown on staging.

FREDRICK AURUM LOCAL UPDATE — 24 NOVEMBER 2026

What changed
- New open-position reconciliation panel on the Gold/USD monitor and the Signal Analyzer. It shows the connected MT5 terminal's read-only snapshot (balance, equity, free margin and every open position with its floating P&L) directly beside the reading on screen, and flags three distinct states: a position in a different instrument than the reading (for example oil sells while the reading is Gold), an open position facing against the reading, and one following it. When the bridge is not connected or no snapshot exists yet, the panel states that the comparison cannot be made instead of showing nothing. Values come only from the bridge's last confirmed snapshot; the panel never sends, modifies or closes orders.

- New GOLD MARKET STRENGTH meter on the Gold/USD monitor: three horizontal bars (buying / selling / neutral) that always total 100% when trusted, scored only from completed M1/M5/H1 candles (EMA alignment, RSI14, MACD, swing structure, ATR regime — missing indicators are skipped and disclosed, never scored as zero). Stale or missing candle windows show INSUFFICIENT DATA instead of numbers. The bars are technical evidence, not probabilities of profit, and the BUY/SELL/WAIT signal and confidence are unchanged and computed separately. An expandable methodology panel lists the exact rules and weights (M1 20% / M5 30% / H1 50%), and a provenance line names the actual data source, status, last update and age. Command Centre now shows the same honest source architecture: prices from Deriv ticks, analysis from completed Deriv/Exness candles, charts displayed by the TradingView widget (display only — not an analysis input), and the market session labelled as a time classification, never as a data provider.

FREDRICK AURUM LOCAL UPDATE — 16 NOVEMBER 2026

What changed
- The local Windows launcher now identifies an MT5 terminal that is already open and saves that exact terminal64.exe path for the Python bridge.
- If more than one MT5 installation is already running, the interactive startup asks which Exness terminal to use rather than silently guessing. Automatic startup reuses a saved path only when it matches a running terminal.
- The start guide clarifies that an account name in the MT5 title bar does not prove the terminal is connected. Wait for connection bars/speed and changing Market Watch prices before connecting in AURUM.
- The complete local package includes the built PC app, bridge, local API, launch scripts, and required runtime source. It excludes credentials, bridge tokens, account details, logs, and machine-specific terminal paths.

Install
1. Extract this ZIP to a normal writable folder. Do not run files inside the ZIP preview.
2. Copy the extracted package contents over the existing local package folder and choose Replace files. Preserve local-only files if prompted; the update ZIP does not contain them.
3. Close the minimized "Fredrick AURUM Local API" window. Run START_ALL_LOCAL.bat from the updated folder and choose the Exness MT5 installation if prompted.
4. In MT5, confirm a live connection (connection speed/bars and updating Market Watch), then press Connect in the local app.

Limit
This update can make the bridge target the correct running MT5 installation, but it cannot restore an Exness network connection or validate account credentials. If MT5 still shows "No connection" or stale prices, resolve that in the MT5 terminal first. The local app was read-only for Exness at that time; superseded 23 November 2026 — manual REAL/DEMO order execution is now enabled (see above).

Privacy
Do not share MT5 passwords, bridge_token.txt, terminal_path.txt, or unredacted startup logs.
